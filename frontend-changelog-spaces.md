# Changelog для фронтенда: переход на пространства

Дата: 2026-10-22. Backend-коммит: `cc8b4a6` — `Unified finances under spaces`.

Изменение несовместимо с прежним API. Личные финансовые маршруты удалены, группы переименованы в пространства. Старые URL и DTO не поддерживаются; переноса старых данных нет.

Для уже подключённых групповых экранов основные изменения — URL, `groupId` → `spaceId`, финансовое владение и удаление типа пространства. Денежные правила прежних групп сохраняются. Финансовые разделы ниже описывают целевой контракт, в том числе отличия при переносе личных экранов.

Все пути ниже указаны относительно настроенного префикса API, по умолчанию `/api/v1`. Пространства, приглашения, профиль и финансы требуют `Authorization: Bearer <accessToken>`. Публичные маршруты регистрации и входа остаются в `/auth`.

## 1. Что нужно поменять в модели приложения

- Удалить переключение между личным и групповым бюджетами. Любые финансы открываются в конкретном пространстве.
- Пользователь может состоять в нуле, одном или нескольких пространствах. Пространство с одним участником подходит для индивидуального учёта и не имеет особого типа.
- Все участники пространства видят все его финансовые данные. Скрытых личных счетов, планов или долгов внутри пространства нет.
- Пространство выбирается явно через `spaceId` в URL. Сервер не выбирает его автоматически и не хранит выбранное пространство в JWT.
- Разделять принадлежность данных пространству и авторство пользователя: `spaceId` — бюджет, `createdBy` — автор, `participantId` — участник расхода.

## 2. Регистрация, профиль и onboarding

### Регистрация без валюты

`POST /auth/register`:

```json
{
  "firstName": "Анна",
  "lastName": "Иванова",
  "email": "anna@example.com",
  "password": "example-password",
  "notes": "Необязательное описание"
}
```

Обязательны `firstName`, `lastName`, `email`, `password`; `notes` необязательно. Удалить поле `currency` из формы и запроса: его передача теперь даёт `400`.

Из профиля, включая `user` в auth-ответах, удалены `defaultCurrency` и `defaultAccountId`. `PATCH /users/me` больше не принимает эти поля. Не использовать их для выбора счёта, форматирования всего бюджета или построения запросов.

### Новый стартовый сценарий

1. После авторизации получить `GET /spaces`.
2. При `items: []` показать выбор: создать пространство или принять приглашение. Аккаунт и профиль при этом полностью доступны.
3. После создания или вступления обновить список и открыть выбранное пространство.
4. Новое пространство пустое: нет автоматических счетов, категорий или других финансовых записей. Предложить явно создать первый счёт с валютой.
5. После выхода, исключения или удаления последнего пространства вернуть пользователя к выбору пространства, сохранив авторизацию.

Не требовать создать своё пространство перед вступлением в чужое. Список пагинирован: `items: []` на произвольной странице сам по себе не означает отсутствие пространств — учитывать `total`.

## 3. Переименование маршрутов

| Прежний контракт | Новый контракт |
| --- | --- |
| `/groups` и `/groups/:groupId/...` | `/spaces` и `/spaces/:spaceId/...` |
| `/group-invitations/preview` | `/space-invitations/preview` |
| `/group-invitations/accept` | `/space-invitations/accept` |
| Личные `/accounts`, `/incomes`, `/expenses`, `/transfers` | Соответствующие `/spaces/:spaceId/accounts`, `/incomes`, `/expenses`, `/transfers` |
| Личные `/transactions`, `/expense-categories`, `/expense-limits` | Соответствующие коллекции внутри `/spaces/:spaceId` |
| Личные `/plans`, `/debts`, `/reports/...` | Соответствующие ресурсы внутри `/spaces/:spaceId` |
| `/debts/:debtId/transactions` и детали такой записи | `/spaces/:spaceId/debts/:id/repayments` и `/:repaymentId` |
| Общие детали/удаление через `/transactions/:id` | Типизированные `/spaces/:spaceId/incomes/:id`, `/expenses/:id` или `/transfers/:id` |
| Личные HTTP-маршруты снимков `/accounts/:accountId/snapshots...` | Удалены; баланс корректируется финансовыми операциями, история доступна через счёт и `timeline` |

В строках с несколькими коллекциями пространственный префикс применяется к **каждой** коллекции. Старые маршруты не перенаправляются; запрос с действующим JWT получает `404`.

Не переносить весь личный контракт механическим добавлением префикса. Например, **`/spaces/:spaceId/incomes/revenue` и `/spaces/:spaceId/transactions/:id` отсутствуют**. Для сводки расходов есть `/expenses/revenue`, для доходов периода — валютные корзины отчётов; детали и мутации операций выполняются по их типу.

## 4. Пространство: DTO, создание и управление

`POST /spaces` принимает только `name` и необязательное `description`. Название — 1–100 символов после trim, описание — до 1000.

```json
{
  "name": "Семейный бюджет",
  "description": "Общие расходы и накопления"
}
```

Пример ответа `201`:

```json
{
  "id": "670000000000000000000001",
  "name": "Семейный бюджет",
  "description": "Общие расходы и накопления",
  "ownerId": "670000000000000000000002",
  "role": "owner",
  "permissions": {
    "manageAccounts": true,
    "manageCategories": true,
    "manageLimits": true,
    "manageTransactions": true
  },
  "createdAt": "2026-10-22T09:00:00.000Z",
  "updatedAt": "2026-10-22T09:00:00.000Z"
}
```

**Пространство использует `id`, финансовые сущности — `_id`.** Не подставлять `space._id` в URL. `type: family | organization` удалён из запросов и ответов пространства; передача `type` отклоняется с `400`. Типы счетов `balance | saving` и операций `income | expense | transfer` сохраняются.

| Действие | Метод и путь |
| --- | --- |
| Список / создание | `GET /spaces`, `POST /spaces` |
| Детали / изменение / удаление | `GET`, `PATCH`, `DELETE /spaces/:spaceId` |
| Участники | `GET /spaces/:spaceId/members` |
| Права участника | `PATCH /spaces/:spaceId/members/:userId/permissions` |
| Передача владения | `POST /spaces/:spaceId/ownership` с `{ "userId": "..." }` |
| Выход | `POST /spaces/:spaceId/leave` |
| Исключение участника | `DELETE /spaces/:spaceId/members/:userId` |

`PATCH` пространства меняет только название и описание; пустое описание очищает его. Владельцу перед выходом нужно передать владение другому действующему участнику либо удалить пространство.

## 5. Приглашения

| Действие | Контракт |
| --- | --- |
| Создать | `POST /spaces/:spaceId/invitations` → `201 { id, token, expiresAt }` |
| Список | `GET /spaces/:spaceId/invitations` → пагинированные метаданные без токенов |
| Отозвать | `DELETE /spaces/:spaceId/invitations/:invitationId` → `204` |
| Предпросмотр | `POST /space-invitations/preview` с `{ token }` → `200 { name, expiresAt }` |
| Принять | `POST /space-invitations/accept` с `{ token }` → `200 { spaceId, role }` |

Из preview удалён `type`; идентификатора пространства в preview также нет. Получать `spaceId` для перехода после принятия приглашения из accept-ответа.

Ссылка действует семь суток и используется один раз. Preview требует авторизацию, не вступает в пространство и не резервирует приглашение. После preview accept может завершиться ошибкой: ссылку могли отозвать или использовать.

Токен передавать исключительно в JSON body, не в query. Не сохранять ответы preview в кэш (`Cache-Control: no-store`). Preview и accept вместе ограничены десятью запросами за минутное окно на пользователя; при `429` учитывать `Retry-After`. Истёкшие, использованные, отозванные и неизвестные ссылки дают одинаковый `400 Invalid invitation`; действующий участник при accept получает `409` без расходования ссылки.

## 6. Финансовые запросы и ответы

Для всех маршрутов раздела базовый путь — `/spaces/:spaceId`.

### Владение и валюта

- Вместо финансовых `ownerType`, `ownerId` и ownership-поля `userId` использовать `spaceId` из ответа.
- Не передавать `spaceId`, `ownerType`, `ownerId`, `userId`, `createdBy` или actor-объекты в финансовых create/PATCH: принадлежность задаётся URL, автора назначает сервер. Лишние поля отклоняются.
- `ownerId` в DTO **пространства**, `userId` участника и `actor.userId` сохраняются: это ссылки на людей.
- Валюта явно задаётся счёту, лимиту, плану и долгу. Валюта дохода/расхода определяется по `accountId`; отдельно передавать `currency` в запрос операции нельзя.
- Доход и расход требуют явно выбранный активный `accountId`; основного счёта нет. Ссылки на счёт, категорию, план или долг другого пространства дают `404`, даже если пользователь состоит в обоих.

### Создание счёта и операций

`POST /accounts`: обязательны `name`, `currency`; необязательны `type` (по умолчанию `balance`), `amount` (начальный остаток, по умолчанию `0`) и `openedAt`. В ответе начальный остаток называется `initialAmount`, текущий — `amount`.

`PATCH /accounts/:id` принимает только `name`. Валюту, тип, начальный остаток и дату открытия изменить нельзя. Для архива — `POST /accounts/:id/archive`, ответ `204`; архивирование сохраняет баланс и историю. Прямые операции доступны как для `balance`, так и для `saving`.

`POST /incomes`: `accountId`, `amount`, `transactionDate`, необязательный `description`. Прежнее личное поле `source` клиентом не передаётся.

`POST /expenses` дополнительно требует `categoryId`; допускает `participantId`, `merchant`, `items`. `participantId` по умолчанию равен автору, явно назначить можно действующего участника того же пространства. Фильтр `participantId` выбирает участника расхода, а не его автора; исторические расходы бывших участников сохраняются.

Для `PATCH` дохода допустимы `amount`, `description`; расхода — также `categoryId`, `participantId`, `merchant`, `items`. Счёт, дата, валюта и автор операции неизменяемы. У дохода и перевода нет `participantId`.

Суммы передаются числами с точностью валюты: JPY — 0, RUB/USD — 2, KWD — 3 знака. Лишняя точность даёт `400`, сервер не округляет такой вход молча. Межвалютные переводы сохраняют фактические `sourceAmount` и `destinationAmount`; разные валюты не суммируются.

### Формы списков

| Ресурс | Ответ списка |
| --- | --- |
| Пространства, участники, приглашения | `{ items, total, page, limit }` |
| Доходы, расходы, общие операции, переводы, планы, долги, история погашений | `{ items, total, page, limit }` |
| Счета, категории, лимиты | Массив объектов |
| Месячные и годовые отчёты | Массив `{ period, currencies }` |

Для пагинации: `page=1`, `limit=20` по умолчанию; максимум `limit=100`. Для планов и долгов архив по умолчанию исключён из списка, включается `includeArchived=true`; в query передавать строки `true`/`false`, не `1`/`0`.

Счета и категории возвращаются вместе с архивными. Не удалять их из клиентского справочника исторических записей; отдельно исключать архивные из выбора для новых операций. Финансовые ответы рекурсивно не содержат `__v`, `mutationVersion`, `lockVersion`, в том числе во вложенных результатах.

### Авторы

Доходы, расходы, переводы и планы содержат `createdByActor`; расходы — также `participantActor`. Долги и погашения сохраняют сведения о своих авторах, отменённые погашения — `cancelledByActor`. Форма Actor:

```json
{
  "userId": "670000000000000000000002",
  "firstName": "Анна",
  "lastName": "Иванова",
  "isAnonymized": false
}
```

При удалении аккаунта, уже на стадии ожидания очистки, имена становятся `null`, `isAnonymized=true`, идентификатор сохраняется. Отображать обезличенного автора без попыток восстановить имя из старого кэша. Выход из пространства сам по себе не обезличивает историю.

## 7. Планы и долги

### Планы

Создание: `POST /plans` с `description`, `targetDate`, положительным `amount`, `currency`, `categoryId`. План принадлежит пространству и не резервирует деньги.

Исполнение: `POST /plans/:id/close` с обязательным `accountId`; можно передать фактическую `amount`, `closingDate`, `description`, `participantId`. Исполнение создаёт один расход, возвращает закрытый план с `expenseId`, сохраняет плановую сумму. Повторное исполнение — `400`. Правка/удаление созданного расхода не открывает план заново.

### Долги

Долг означает «пространству должны». Создание: `POST /debts` с `debtor`, положительным `principalAmount`, `currency`; необязательны `description`, `dueDate`. `remainingAmount` и `status` вычисляет сервер, передавать их нельзя. `principalAmount` можно изменить только до первой записи погашения, включая впоследствии отменённую; затем — `409`.

- История: `GET /debts/:id/repayments`, детали — `GET /debts/:id/repayments/:repaymentId`. Отменённые записи остаются в истории.
- Погашение: `POST /debts/:id/repayments` с `amount`, `repaymentDate` и обязательным JSON boolean `isIncome`.
- При `isIncome=true` обязателен активный счёт того же пространства и валюты; создаётся связанный доход. При `isIncome=false` поле `accountId` нужно **не передавать**.
- Ответ погашения — `201 { debt, repayment }`; обновлять в UI и долг, и историю, а для финансового погашения — счёт и отчёты.
- Отмена: `POST /debts/:id/repayments/:repaymentId/cancel` без полей body/query → `200 { debt, repayment }`. Повторная отмена — `409`.
- Связанный доход нельзя отдельно исправить или удалить: обычный income API возвращает `409` для активного счёта. Исправление погашения — отмена и новая запись.

Планы и долги архивируются через `POST /:id/archive` с `204`. Архивные детали и история доступны, мутации заблокированы. Для очистки срока долга разрешён `PATCH /debts/:id` с `dueDate: null`; не распространять это правило на все nullable/optional поля.

## 8. Отчёты и агрегаты

Отчёты: `GET /reports/months` и `GET /reports/years`. Параметры: `fromDate`, `toDate`, `categories` (ID через запятую). Периоды — полные UTC-месяцы/годы, `period` имеет вид `YYYY-MM` или `YYYY`.

**Изменение относительно личных отчётов:** без `fromDate` начало — 1 января текущего UTC-года, а не самый ранний снимок. Для показа прошлых лет фронту нужно явно задавать исторический диапазон. Обратный диапазон и диапазон более 100 лет дают `400`.

Каждый период содержит `currencies`, в каждой корзине: `currency`, `incomes`, `expenses`, `transfersIn`, `transfersOut`, `balance`, `saving`, `expensesByCategory`. `balance` относится к счетам `balance`, `saving` — к накопительным; не складывать разноимённые валюты в общий числовой итог. Переводы не являются доходами или расходами. Пустое пространство возвращает `currencies: []`, без выдуманной валюты профиля.

`GET /expenses/revenue` возвращает `{ totalRevenue, currencies, fromDate?, toDate? }`. В `currencies` элементы `{ currency, totalRevenue }`; верхний `totalRevenue` равен `0` при отсутствии операций, сумме при одной валюте и `null` при нескольких. Не трактовать `null` как отсутствие расходов.

## 9. Права и UI действий

Использовать `role` и все четыре `permissions` из DTO выбранного пространства. Они приходят и в списке пространств; не нужно искать собственную запись на первой странице участников.

| Возможность | Кто может |
| --- | --- |
| Читать все финансы; создавать операции, переводы, планы и долги | Любой действующий участник |
| Управлять счетами | `manageAccounts` |
| Управлять категориями | `manageCategories` |
| Управлять лимитами | `manageLimits` |
| Править/удалять чужие доходы и переводы; управлять чужими планами/долгами | Владелец либо `manageTransactions` |
| Править/удалять расход | Также действующий автор и участник этого расхода |
| Переназначать участника расхода | Владелец, автор либо `manageTransactions` |
| Править свои доходы/переводы; управлять своими планами/долгами | Также действующий автор соответствующей записи |
| Управлять пространством, приглашениями, членством и выдачей прав | Только владелец |

Владелец имеет все четыре финансовых права. Новый или повторно вступивший участник — четыре `false`. Права настроек не дают доступа к чужим финансовым мутациям; `manageTransactions` не даёт управления настройками или участниками. При передаче владения прежний владелец становится участником без делегированных прав.

Сервер проверяет текущее членство и права на каждом запросе, в том числе со старым JWT. Клиентское скрытие кнопки не заменяет обработку `403` после изменения прав.

## 10. Ошибки, кэш и жизненный цикл

| HTTP | Обработка на фронте |
| --- | --- |
| `400` | Ошибка DTO, неизвестное/удалённое поле, недопустимые деньги/даты или состояние; для приглашений также единая ошибка недействительной ссылки |
| `401` | Нет действующей авторизации; существующая auth/2FA-логика сохраняется |
| `403` | Членство есть, полномочий на действие нет; обновить права и состояние действий |
| `404` | Пространство/объект недоступен, отсутствует, удалён или заморожен архивом для данной мутации; проверить доступность выбранного пространства |
| `409` | Конфликт состояния: исторические зависимости, попытка отдельной правки дохода погашения, выход владельца и другие предметные ограничения |
| `429` | Для preview/accept учитывать `Retry-After` |
| `503` | Операция не завершена из-за сервисной ошибки; финансовые изменения откатываются, не обновлять UI как при успехе |

Форма ошибки остаётся `{ statusCode, message, error, path, timestamp }`; `message` — строка либо массив строк. Основной признак — HTTP/statusCode, не текст `error`.

Ключи кэша, подписки и незавершённые запросы должны учитывать `spaceId` и фильтры. При переключении пространства очищать выбранные account/category/plan/debt ID; не допускать, чтобы поздний ответ прошлого пространства заменил текущий экран.

Выход/исключение лишает доступа даже к собственным старым операциям. Удаление пространства закрывает доступ всем, завершает членства и отзывает ожидающие приглашения; история сохраняется на сервере, восстановления и просмотра удалённого пространства через API нет. Удаление пользователя сохраняет финансы с обезличенным авторством; владелец сначала передаёт или удаляет свои пространства. Успешное удаление пользователя по-прежнему возвращает `202` и отзывает авторизацию.

Архив счёта замораживает создание, изменение и удаление его финансовых операций, сохраняя чтение и влияние на отчёты. Удаление счёта с ненулевым начальным остатком или любой историей, включая удалённые операции, возвращает `409`. Архивирование не обнуляет деньги. Для `204` не пытаться разбирать JSON body.
