# Design

## Context

Мотивация и границы поведения описаны в proposal.md и трех delta specs.
`Accounts` получает счета на конец выбранного месяца. `AccountRow` отдельно управляет
`Collapsible` и лениво запрашивает первую страницу из 10 переводов. Отдельный `Transfers`
сейчас предоставляет действия управления. Формы переводов и их инвалидация уже существуют.

`GET /transactions` поддерживает `accountId`, период, `page`, `limit` и единственный
`transactionType`: `income`, `expense` или `transfer`. Без типа ответ смешанный.
Ответ содержит `items`, `total`, `page`, `limit`. Контракт клиента не гарантирует серверную
сортировку; это важно для объединенной истории. `GET /transfers` поддерживает счет, период
и серверную пагинацию. У счета уже есть необходимые поля сведений.

## Goals / Non-Goals

**Goals:** использовать существующие API и формы; изолировать состояние окна от раскрытий;
обеспечить правильные страницы без скрытой потери операций.

**Non-Goals:** менять краткую историю в строках счета, добавлять редактирование доходов/расходов,
строить графики счета, менять период внутри окна или вводить новые зависимости.

## Decisions

### 1. Независимое окно и сохранение раскрытия

`Accounts` хранит выбранный id счета отдельно от `openAccountIds`. Выбранный объект берется
из актуального результата запроса счетов, чтобы после мутации баланс обновлялся.
Название и баланс объединяются в доступную кнопку; стрелка остается соседней кнопкой,
без вложенных интерактивных элементов. Нажатие стрелки не открывает окно и наоборот.
Отказ от замены Collapsible сохраняет согласованный пользователем сценарий краткого просмотра.

Окно с историей разместить рядом с Accounts в widget slice: оно объединяет несколько entities
и действия features. Widget может импортировать manage-transfer, но manage-accounts не должен
импортировать другую feature. Чистую подготовку запросов/данных держать в соответствующих
entity query/model модулях и экспортировать через публичный API. Новые cross-entity импорты,
если понадобятся, допускаются только через `@x`.

### 2. Полная история доходов/расходов на существующем API

Использовать два типизированных списка `/transactions`: `income` и `expense`, каждый с
`accountId`, `fromDate`, `toDate`. Для выбранного счета и месяца лениво получить все страницы
этих двух списков с допустимым API размером страницы до 100, используя метаданные ответа.
Объединить результаты, удалить дубликаты по id, отсортировать по дате убывания и id убывания,
после чего показывать UI-страницы по 10 записей. До завершения обоих списков не выдавать
частичный набор за полную страницу. Ошибка любой необходимой страницы — ошибка этой таблицы.

Это дает корректный общий порядок и общее количество без предположения о серверной сортировке
и без нового backend API. Подготовленный набор кэшируется в transactions query family по счету
и периоду, чтобы существующая инвалидация переводов затрагивала и его; UI-страница не требует
повторной полной загрузки. Запросы выполняются только при открытом окне.

Отклоненные варианты: фильтровать переводы из одной смешанной страницы (неверные размер и total);
склеивать одноименные страницы income/expense (неверный глобальный порядок);
вводить новый серверный фильтр (его поддержка в доступном контракте не подтверждена).

### 3. Пагинация переводов

Использовать существующий `transfersQueryOptions.findAll` с `accountId`, периодом, страницей
и `limit: 10`. До реализации проверить на доступном API, что страницы идут от новых записей
к старым с устойчивым порядком для одинаковых дат. Если этот контракт не выполняется,
использовать ту же стратегию полной загрузки страниц за месяц и локальной сортировки,
что и для доходов/расходов; не сортировать отдельно страницы и выдавать это за глобальный порядок.
Эта проверка не требует изменения требований или нового API.

Счетчики страниц двух таблиц независимы. Сессия окна, id счета и период сбрасывают их на 1.
При смене контекста старые записи не показываются под новым месяцем. После удаления переводов
страница ограничивается новым количеством страниц. Краткое раскрытие сохраняет свой
отдельный запрос `page: 1, limit: 10` и свое состояние.

### 4. Представление и действия

Заголовок окна содержит счет и выбранный месяц; сведения включают тип, валюту, баланс
на конец месяца, дату открытия и initialAmount. Доходы/расходы показывают дату, тип,
сумму и необязательное описание. Переводы показывают дату, второй счет и подписанную сумму
стороны выбранного счета. Названия разрешаются по полному списку счетов, включая архивные,
с локализованным fallback. Паттерн вычисления эффекта из account-presentation переиспользуется
внутри widget без изменения существующего раскрытия.

В окне используются существующие Create/Edit/DeleteTransferButton. Create получает
необязательный initialSourceAccountId, который при доступности имеет приоритет над default account;
Отправитель фиксирован и отображается как read-only информация вместо селектора. Вложенные окна формы/подтверждения сохраняют
окно счета и возвращают фокус в него. Инвалидация остается в transfers.query и обновляет
оба счета, обе истории, раскрытия и агрегаты. Ошибка обновления после успешной мутации
не превращает сохранение в ошибку.

У каждой таблицы собственные skeleton, empty и error/retry. Данные того же контекста
сохраняются при фоновом обновлении. Использовать существующий Dialog, ограниченную высоту
с внутренней вертикальной прокруткой и адаптивную раскладку без переполнения страницы.

## Risks / Trade-offs

- [Много доходов/расходов за месяц] → Полная загрузка выбранного месяца дороже одного запроса;
  загружать только при открытии, кэшировать и соблюдать лимит API. При подтвержденной проблеме
  производительности отдельно согласовать серверный комбинированный фильтр и сортировку.
- [Недокументированный порядок переводов] → Проверить API; предусмотрен корректный локальный fallback.
- [Изменение истории между запросами страниц] → Дедупликация по id и полное обновление набора после
  инвалидации; доступный API не предоставляет snapshot-консистентность нескольких запросов.
- [Вложенные модалки] → Проверить Escape, возврат фокуса, pending и ошибку удаления вручную.
- [Удаление виджета скрывает управление] → Сначала интегрировать все действия в окно, затем удалить виджет.

## Migration Plan

Изменение фронтенда без миграции данных и новых переменных окружения. Добавить запросы и окно,
связать действия, затем удалить Transfers и его неиспользуемый slice. Проверить три обязательные
команды репозитория и UI. Откат — вернуть подключение виджета и прежнюю строку счета;
данные и API остаются совместимыми.


## Implementation notes

Для переводов выбран предусмотренный fallback: полная загрузка страниц за выбранный месяц,
стабильная локальная сортировка и UI-пагинация. Контракт сортировки реального backend не подтвержден;
проверки используют изолированный тестовый API с намеренно неупорядоченными записями.
Общий загрузчик страниц находится в shared/lib/paginated-history и используется обеими entities;
запросы остаются в соответствующих query families. Направленные проверки подтверждают обход
всех страниц, учет фактического limit ответа, дедупликацию, порядок и обработку ошибки страницы.


## UI refinements

Пагинация использует доступные кнопки со стрелками и выравнивается вправо.
Кнопка создания перевода — плюс рядом с заголовком «Переводы», без видимой текстовой подписи.
Общие Dialog/AlertDialog Backdrop используют forceRender: Base UI иначе скрывает подложку
вложенных окон. При этом вложенные окна сохраняют свой фокус и жизненный цикл.

Строка отправителя в форме создания: «Списать с текущего счета» слева и баланс в валюте
счета справа, без имени счета. Ошибка отсутствующего получателя: «Выберите доступный счет».


## Current account management

Переиспользовать ManageAccountsButton с необязательным accountId: общий режим сохраняет весь
список и создание счетов, режим текущего счета показывает только его и скрывает создание.
В шапке деталей разместить доступную кнопку «Управление счетом». Переименование, выбор основным,
архивация/удаление, ошибки, pending и инвалидация используют существующие обработчики feature.
Режим текущего счета не подписывается на глобальные запросы открытия общего управления.
После подтвержденной архивации/удаления закрыть оба окна и вернуть фокус на стабильную кнопку
общего управления в Accounts. При ограниченном удалении предложить переход к подтверждению
архивации. При переименовании обновлять данные из query, сохраняя исторический период деталей.
Создание нового счета не относится к редактированию выбранного и остается в общем режиме.
