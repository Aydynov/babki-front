# Design

## Context

Мотивация описана в proposal.md. Изменение затрагивает widget, feature и доступность вложенных окон,
поэтому нужен общий design. `Accounts` уже получает все счета на конец выбранного месяца,
а `groupAccounts` отбрасывает архивные. `ManageAccountsButton` совмещает общий список, создание
и режим одного accountId. `AccountSelect` через `requestAccountManagement` открывает создание
при отсутствии подходящего счета. В деталях сейчас всегда смонтирован `CreateTransferButton`.

Завершенный `account-details-dialog` пока не синхронизирован в основные specs. Его решения
о создании в общем управлении и возврате фокуса на общую кнопку заменяются этим change;
остальные требования деталей остаются в силе. Существующие artifacts того change не редактируются.

## Goals / Non-Goals

**Goals:** переиспользовать запросы, строки, историю и мутации; локализовать режим в widget;
сохранить стабильный фокус и открытие создания из operation forms.

**Non-Goals:** восстановление архивных счетов, новый API, изменение финансовых ограничений,
глобальный или URL-параметр режима, переработка истории и пагинации, новые зависимости.

## Decisions

### 1. Локальный режим и общая группировка

Хранить `active | archived` в `Accounts`, начальное значение `active`. Расширить `groupAccounts`
параметром режима с текущим активным значением по умолчанию; отбирать по `archivedAt`, сохранив
порядок типов и единую сортировку. Использовать тот же period-aware запрос и полный `accountNames`.
Отдельный запрос архива и второй widget дублировали бы уже загруженные данные и представление.
Статус архива определяется возвращенным `archivedAt`, а выбранный месяц продолжает определять баланс.

Смена месяца сохраняет режим. Переключение списков сохраняет `openAccountIds`; id скрытого списка
не отображаются до возврата. Выбранный счет и детали не переносятся в другой режим. Состояние
не сохраняется между размонтированиями: это локальная навигация, без новой настройки пользователя.

### 2. Шапка и фокус

Одна стабильная кнопка переключения меняет иконку и accessible name: архив / возврат
(`LucideArchive` / `LucideArrowLeft`, предлагаемые иконки). В активном режиме она слева от `+`.
В архивном режиме `+` отсутствует в DOM, заголовок — «Архивные счета»; при пустом результате
показать «Архивных счетов нет». Кнопку переключения показывать и при пустом списке.
Иконки и формулировки — локальные UI-решения, новые строки идут через i18next.

Ref стабильной кнопки переключения заменяет `managementTrigger` как fallback после успешной
архивации/удаления. Обычное закрытие деталей возвращает фокус в исходную строку. После lifecycle
закрываются вложенные окна и детали, режим сохраняется; использовать существующую обработку
очередности focus cleanup. Возврат на `+` непригоден, поскольку в архиве кнопка скрыта.

### 3. Создание и управление в одной feature

В `manage-accounts` выделить `CreateAccountButton` с отдельным диалогом формы и публичным экспортом.
Перенести существующие создание, валидацию, reset и обработку ошибок без изменения payload и правил.
`ManageAccountsButton` оставить для обязательного accountId: только управление выбранным счетом.
Это убирает общий список и двусмысленность режима вместо добавления третьего режима в большой компонент.
Сохранять существующие мутации и инвалидацию, не вводить общий универсальный контроллер диалогов.

Подписку `subscribeAccountManagementRequests` перенести в создание. Компонент создания держать
смонтированным и в архивном режиме, скрывая только его trigger: внешняя команда из `AccountSelect`
продолжит открывать форму. Она не меняет режим списка и не добавляет `+` в архив. После закрытия
возвращать фокус к исходной внешней кнопке; после открытия из шапки — к `+`.
Если после создания первого подходящего счета исходная кнопка заменена селектором, при закрытии
возвращать фокус к доступному селектору в исходном диалоге вместо удаленного элемента.
Название существующего event API можно сохранить ради минимального объема изменений.

### 4. Архивные детали и ограничения

Переиспользовать `AccountRow` и `AccountDetailsDialog`; статус явно виден в управлении.
Для архивного счета не выводить создание перевода в деталях. Уже существующие фильтры
допустимости исключают архивные счета из новых операций и выбора основным; сохранить их.
Переименование и удаление используют те же подтверждения и ошибки. История и существующие
действия над историческими переводами сохраняются в пределах текущих ограничений API.
Восстановление счета не добавляется.

## Risks / Trade-offs

- [Скрытый trigger ломает внешний вход создания] → сохранять подписчика смонтированным,
  проверять создание из пустого селектора в обоих режимах, включая возврат фокуса.
- [Удаленная строка становится целью фокуса] → после успешного lifecycle использовать стабильную
  кнопку переключения и проверить порядок закрытия вложенных окон.
- [Архивный счет получает создание перевода] → скрыть соответствующее действие в деталях,
  сохранить entity eligibility без расширения доступности новых операций.
- [Старый change возвращает общее управление при sync] → при последующей синхронизации сначала
  учитывать `account-details-dialog`, затем эти delta specs; его `Current account management`
  согласовать с новой точкой создания/фокуса в рамках sync, не меняя старые artifacts сейчас.
- [Нет общего рабочего test script] → обязательные lint, architecture и build дополнять
  направленными проверками и ручным просмотром; команды и ограничения записать в verification.md.

## Migration Plan

Изменения только на клиенте, без миграции данных. Реализовать фильтрацию и переключение, разделить
диалоги, подключить архивные детали, затем выполнить проверки из tasks.md. При откате вернуть
предыдущий frontend: формат API и сохраненные счета не меняются.

## Account creation layout refinement

Использовать существующий shared Select для типа и валюты, без новых зависимостей и изменения
общего компонента. Trigger растянуть по ширине поля и выровнять по высоте Input (h-11).
Убрать border/rounded/padding с формы: ее контейнером уже является Dialog.
Каждому полю добавить видимый label, связанный с уникальным id через React useId.
Тип и валюта используют две колонки от sm; название, сумма и дата занимают отдельные полные строки.
Ошибка точности располагается под суммой и связывается с input через aria-describedby/aria-invalid.
Начальное и reset-значение amount — пустая строка; существующий Number(values.amount) уже
преобразует ее в numeric 0. Ограничения точности и отрицательных значений сохраняются.
