# Design

## Context

Мотивация и область описаны в proposal.md. `PlanDetailsDialog` уже управляет режимами view/edit/execute,
но использует Dialog и закрывается на Escape во всех режимах. Формы размещают действия в заголовке;
`PlanView` содержит отдельные кнопки и собственную мутацию архива. Участник выполнения — нативный select.
`getExecutePlanFormValues` оставляет accountId пустым; фильтрация уже исключает архивные счета и чужую валюту.

Образцы: `ExpenseDetailsDialog` обрабатывает причину закрытия и возврат фокуса;
`ExpenseForm` использует нижние действия и общий Select; окно лимитов использует меню в заголовке,
а строки лимитов — `LucideUndo2` для восстановления. Общий ScrollDialog уже содержит прокрутку и панели.
Дизайн нужен для согласования состояния нескольких режимов с асинхронной загрузкой счетов.

## Goals / Non-Goals

**Goals:** сохранить существующие операции и их контракты, централизовать отмену и блокировку закрытия,
переиспользовать публичные UI-примитивы без новой общей абстракции форм.

**Non-Goals:** менять создание плана, окно связанного расхода, правила разрешений, серверные схемы,
инвалидацию кеша, расчёт фактической суммы или общий компонент ScrollDialog.

## Decisions

### 1. Одна оболочка и прежние три режима

Заменить внешний Dialog на ScrollDialog.Base/Content; каждый режим оформляет свой Layout,
формы используют flex-контейнер с min-h-0. Передавать действия через actions, меню — через headerActions.
Не добавлять вложенные scroll-контейнеры. Альтернатива с тремя независимыми модалками усложняет фокус
и восстановление деталей без пользы для задачи.

Обрабатывать escape-key на уровне владельца режима: edit/execute -> view с очисткой ошибки мутации;
view -> закрытие. Крестик и backdrop закрывают всю модалку. Отмена размонтирует форму, повторный вход
берёт актуальный activePlan. Внутренний popup получает Escape первым. После отмены фокус возвращается
к меню редактирования или кнопке выполнения, после закрытия — к элементу виджета.

### 2. Единый учёт незавершённых операций

Архивирование сейчас живёт внутри PlanView и не входит в isPending родителя. Поднять мутацию
или явно передавать её pending владельцу окна, чтобы закрытие и конфликтующие операции блокировались
для всех четырёх мутаций. Меню открывает отдельное подтверждение архива/удаления после закрытия popup.
Сохранить ограничения editable/canManage, доступность исполнения по категории и историческую связь.
Не пытаться вложить существующую кнопку ConfirmActionButton внутрь Menu.Item; отделить подтверждение
от триггера в пределах manage-plan, избегая новой универсальной системы подтверждений.

### 3. Детерминированный выбор счёта

Дополнить локальную модель выполнения выбором первого balance из eligibleAccounts, иначе первого saving.
Порядок API сохраняется; понятие основного счёта не требует нового флага в схеме Account.
Инициализация учитывает как кешированные, так и позже загруженные счета. Обновление списка меняет
accountId только при пустом или недопустимом выборе; допустимый ручной выбор не перезаписывается.
Отсутствие подтверждённых данных не создаёт фиктивного значения и блокирует отправку.

Сброс использует ту же функцию defaults: плановые сумма/описание, сегодня, пустой participantId,
приоритетный доступный счёт; сбрасывает метаданные ошибок формы и ошибку мутации.
Альтернатива с form.reset на каждом refetch потеряет введённые значения, поэтому не используется.

### 4. Поля и действия следуют существующему виду

В редактировании нижняя панель: Button.Icon с LucideArrowLeft, затем сохранение.
В выполнении: стрелка, Button.Icon с LucideUndo2 и подсказкой «Сбросить», затем выполнение.
Крестик остаётся справа в заголовке. У всех иконок aria-label и title.

Для участника использовать публичный Select, стили и вариант единственного участника из ExpenseForm.
Сохранить пустое значение модели как отсутствие явного participantId в запросе; визуальный вариант
по умолчанию соответствует текущему пользователю, без автоматической отправки его идентификатора.
Отдельные label/id для всех полей, placeholders для пустого ввода; для нативного date учитывать,
что браузер может показывать маску даты вместо placeholder. Не менять тип ввода ради плейсхолдера.
Подписи, подсказки и названия действий добавить в существующие русские переводы.

### 5. Сведения как адаптивная сетка

Использовать незаключённую в рамки сетку по образцу расходов и лимитов: описание занимает обе колонки,
затем сумма/категория, дата/статус, автор. На мобильном одна колонка с тем же DOM-порядком.
Статус архива и автор получают подпись и значение; неизвестный автор — «—».
Предупреждения и ошибки остаются отдельными сообщениями; существующее сравнение сумм сохраняется.

## Risks / Trade-offs

- [Форма меняется при refetch] → обновлять только недопустимый accountId, проверять сохранность остальных полей.
- [Escape закрывает сразу два уровня] → использовать причины Base UI и вручную проверить popup и подтверждения.
- [Архивирование не блокирует родительское окно] → включить его pending в общий контроль до переноса меню.
- [Нет рабочего общего тестового раннера] → точечные модельные проверки через Vite SSR и node:test,
  ручная проверка интерактивной навигации; не заявлять покрытие через bare node --test.

## Migration Plan

Изменение клиентское, миграция данных и новые зависимости не требуются. После проверок поставляется
обычной сборкой фронтенда; откат возвращает прежние компоненты без изменения сохранённых планов.
