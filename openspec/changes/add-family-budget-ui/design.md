# Design

## Context

Мотивация и согласованный объём — в [proposal.md](proposal.md). Действующие требования личного учёта
сохраняются; новые `group-*` capability описывают отдельный групповой контекст и его отличия.

Сейчас `MainPage` собирает финансовые widgets без бюджета; entities вызывают личные маршруты,
ключи Query содержат сущность и фильтры, но не владельца. Выбранный период хранится в Zustand.
Существуют account details, управление счетами/переводами, категории/лимиты, формы планов/долгов,
auth boundary, подтверждение сессии и TOTP/recovery. Регистрация всегда переходит в `/main`.

Контракт исследован в соседнем `babki-back` на 2026-10-18:

- [Группы](../../../../babki-back/docs/groups-api.md), [финансы](../../../../babki-back/docs/group-finances-api.md),
  [финальная сверка](../../../../babki-back/docs/family-budget-contract-audit.md).
- Group DTO имеет `id`, `role`, четыре `permissions`; financial DTO — `_id`, `ownerType/ownerId`,
  actors и origin без обязательных внутренних `__v`/lock/mutation полей.
- Счета/категории/лимиты/отчёты — массивы, остальные списки — страницы. У расходов category — ID.
- В группах нет `incomes/revenue`, `accounts/:id/snapshots`, `accounts?toDate`, личного default account,
  поля source у дохода и личного `/debts/:id/transactions`. Групповая история долга — `/repayments`.
- Групповые amount/snapshot могут быть отрицательны. Точность валюты задаёт minor units, а не fixed2.

## Goals / Non-Goals

**Goals:**

- Переиспользовать существующие widgets и формы с явным владельцем данных, сохраняя FSD.
- Обеспечить проверяемую изоляцию пользователя/бюджета и согласованность мутаций при навигации.
- Использовать действующий API без выдуманных маршрутов, не требуя новых зависимостей.
- Дать конкретный маршрут реализации и проверки без выполнения реализации в этом change proposal.

**Non-Goals:**

- Не создавать второй полностью независимый dashboard или универсальную систему произвольных scopes.
- Не объединять несовместимые входные DTO ради общего интерфейса и не рефакторить несвязанные части.
- Не менять бэк, конфигурацию OpenSpec, инфраструктуру production или существующие архивные changes.

## Decisions

### 1. URL — источник активного бюджета, preference — только стартовое значение

Маршруты:

| Путь | Поведение |
| --- | --- |
| `/main` | После подтверждения пользователя разрешить сохранённый бюджет, иначе личный; заменить URL каноническим |
| `/main?budget=personal` | Явный личный бюджет, не переопределяется preference |
| `/main?budget=<groupId>` | Валидировать ObjectId и доступ через GET группы, затем показывать её dashboard |
| `/groups` | «Мои группы», пагинация и создание семьи |
| `/groups/new` | Создание семьи; после POST переход к её dashboard с продолжением настройки |
| `/groups/$groupId` | Настройки явно указанной группы; сами по себе не меняют последний выбор dashboard |
| `/join#token=...` → `/join` | Внешний вход приглашения; извлечение секрета до перенаправления на auth |

Некорректный budget-параметр нормализуется в personal с объяснением; недоступная группа — тот же
fallback после подтверждённого 404. Сеть/503 показывают retry, не стирая выбор. Financial 404 сначала
обрабатывается как недоступная запись; если есть подозрение потери членства, перечитать саму группу.

Предпочтение в localStorage содержит только `{kind, groupId?}` под ключом подтверждённого userId,
без имён, денег и прав. Не транслировать storage events в активные вкладки: явный URL каждой вкладки
независим. Ошибки storage не блокируют навигацию. Смена бюджета не меняет месяц/год; пользователь
может переключать их существующими средствами. Миграция текущего ключа периода не требуется.

Альтернатива — только глобальный Zustand persist — проще локально, но теряет смысл ссылок,
назад/вперёд и независимость вкладок. Два отдельных маршрута dashboard дублировали бы композицию.

### 2. Явный scope через FSD и захват контекста до запроса

В `shared/types` разместить только нейтральный discriminated type BudgetScope:
personal с userId, group с userId/groupId. `entities/budgets` предоставляет подтверждённый активный
контекст через публичный API/provider; компоновка route/page связывает его с `entities/groups`.
Сущность groups владеет Zod DTO, API, ключами группы, участников и приглашений.

Финансовые entities получают scope явным аргументом в query/mutation factories. Не читать текущий
бюджет из глобального store внутри Axios interceptor: поздняя отправка не должна менять адресата.
Пути и входные/выходные схемы выбираются в owning entity по scope. Общие UI-примитивы не знают
о группах. Cross-entity зависимости используют только целевые `@x` API, остальное — public index.

Features: выбор бюджета, создание семьи, настройки/участники, приглашения/вступление. Новые pages
групп и вступления используют эти features, существующие widgets получают scoped query options.
При смене scope финансовое поддерево получает новый key: локальные страницы, открытые детали
и формы не протекают между бюджетами. Период остаётся снаружи keyed-поддерева.

### 3. Кэш и мутации изолированы по пользователю и бюджету

Внутри каждого entity сохранить собственное семейство ключей и добавить scope до фильтров,
например `['accounts', userId, 'group', groupId, 'list', filters]`. У сущности есть scoped-prefix
для инвалидации её списков/деталей. Личные ключи также содержат подтверждённую identity.

Матрица инвалидации остаётся в entity query-модулях с разрешёнными @x API:

| Мутация | Обновляемые данные того же scope |
| --- | --- |
| Доход/расход | owning lists/details, счета, ledger-остатки, операции, отчёты, лимиты при расходах |
| Перевод | обе стороны, transfers/transactions, ledger-остатки, отчёты |
| Исполнение плана | планы и все зависимости нового расхода |
| Погашение/отмена | долг/история и при financial доходы, счета, ledger, операции, отчёты |
| Счёт | account lists/details, eligible selectors, ledger и финансовые зависимости |
| Права/членство | group lists/detail/members и доступные действия; потеря доступа очищает group scope |

Запросы чтения передают AbortSignal. Старый ответ может заполнить только старый scope, но не
новую вкладку/форму. Перед onSuccess side effects проверять, что захваченная identity ещё активна:
logout/смена пользователя не должны повторно наполнить очищенный кэш. В рамках той же identity
навигация не отменяет фиксацию результата в исходном scope. Ошибка refetch не меняет успех мутации.
Для финансовых POST, создания счёта/группы и приглашений retry выключен: idempotency key у API нет.

### 4. Разные wire DTO, общая модель представления

Не ослаблять личные схемы до произвольных optional-полей. Определить отдельные group DTO внутри
соответствующих entities и нормализовать проверенные ответы для общего UI:

- accounts/snapshots разрешают отрицательный текущий amount; initialAmount остаётся >=0;
- group expense.category валидируется как ID; category badge разрешается по каталогу группы;
- actors сохраняются как `{userId, firstName:null|string, lastName:null|string, isAnonymized}`;
- origin сохраняется для перехода к плану/долгу и выбора разрешённых действий;
- group plan не требует userId; group debt не принимает remainingAmount/status, dueDate может быть null;
- group repayment имеет отдельный response и compound `{debt, repayment}`, не личный debt transaction;
- не требовать внутренние счётчики и не отправлять вычисленные/серверные поля обратно в API.

Общие money helpers проверяют конечность, положительность и minor units валюты, в групповых
формах не остаётся `.min(0.01)` для всех валют. Для группового лимита допускается zero, как на бэке.
Текущие личные ограничения и UX сохраняются, кроме необходимых общих проверок валютной точности.

### 5. Доходы и исторический остаток без отсутствующих endpoints

Групповые доходы и сравнение с прошлым месяцем получают значения из `reports/months`; детали —
из `/incomes` с пагинацией и currency. Не создавать group `/incomes/revenue` вызов. Годовой запрос
группы явно получает нужные fromDate/toDate, иначе default бэка ограничится текущим годом.

Отдельный счёт за выбранный месяц нельзя вычислять по текущему amount, сумме одной страницы или
последним 20 timeline-записям. Для группы использовать account-specific query historical ledger:
`GET /groups/:id/transactions?accountId=...&toDate=<UTC month end>&limit=100&page=N`, без fromDate,
со всеми страницами до total. Начать с initialAmount, если openedAt не позже границы; прибавить
income, вычесть expense, для transfer применить только сторону открытого счёта. Вычислять деньги
в minor units с существующими money helpers/целочисленной арифметикой. До openedAt вернуть 0.
Не передавать неподдерживаемые snapshotId/toDate в account queries и не вызывать личный snapshot API.

Ключ historical query содержит scope/accountId/UTC end. Переиспользовать полученный кэш, не создавать
отдельные одинаковые запросы в строке и деталях; после финансовых действий инвалидировать зависимые
исторические периоды. Неполный ledger оставляет loading/error, не выдуманный остаток. Постраничные
чтения не образуют серверный snapshot: смена total/дубликаты требуют повторить чтение явно, не
показывать заведомо смешанный результат. Редактирование существующей записи между страницами может
потребовать пользовательского refresh; API не предоставляет revision для строгого snapshot чтения.

Альтернатива — показывать только текущий group amount — нарушила бы смысл уже выбранного месяца.
Отдельный endpoint исторического остатка эффективнее, но не входит в этот change и не блокирует
реализацию на существующем контракте. Первая реализация корректна по данным полного ledger,
стоимость чтения растёт с историей, это ограничение явно проверяется на пагинированных fixtures.

### 6. Периоды и семейные финансовые формы

Из выбранных календарных year/month строить полные UTC-границы для групповых запросов и лимитов;
не использовать локальный endOfMonth как UTC instant. Ввод даты без времени трактовать для
семейной операции как выбранный UTC-день. Показать пользователю дату, не сдвигая её в соседний день
при форматировании. Личные правила периодов этим change не переопределяются.

Семейные расходы не показывают participant selector/filter и не отправляют participantId в create
или PATCH; это сохраняет историческое назначение и server default. Автора показывать в деталях,
без лишних столбцов в основной таблице. Прямые group income/expense допускают активный saving;
личный income по существующей спецификации продолжает использовать balance и source.
Группового default account нет: пользователь явно выбирает счёт, даже при одном доступном.

Переводы остаются в деталях счёта. Контрагент выбирается только из того же scope; суммы/курс
переиспользуют существующие формы, server funds validation на дату остаётся окончательной.
У дохода с origin=debt вместо edit/delete — переход к долгу и отмена через repayments. У расхода
плана обычные разрешённые edit/delete сохраняют закрытый план и историческую связь.

### 7. Роли и настройка семьи

Создание принимает только name/type=family. Уже существующие organization тоже показываются
и используют те же права/финансовые формы; отдельного мастера организации не добавлять.
После create выбрать group URL и показать компактную последовательность первого счёта/приглашения,
оба шага можно пропустить. Успешное создание группы не откатывать из-за ошибки следующего шага.
После перезагрузки предложить недостающий счёт по реальным данным; приглашения остаются в настройках.

У владельца в участниках доступны четыре подписанных переключателя и «Дать полное управление
финансами», отправляющее все четыре true одним PATCH выбранного userId. Не включать права на accept,
не называть действие административной ролью. Собственные эффективные права читать из group DTO.
Обновлять их при focus/входе в контекст и после 403. Каталог members пагинируется, не считать
первую страницу полным списком. Настройки и приглашения имеют независимые loading/error состояния.

Проверки прав — чистые функции от scope, актуального group context, currentUserId, row.createdBy,
participantId, origin и archivedAt; использовать их одинаково в buttons и forms. Бэк всё равно
проверяет каждую мутацию. Владелец не может выйти без передачи; передача сбрасывает его права;
удаление группы прекращает доступ всех участников. Все последствия указать в подтверждениях.

### 8. Вступление и авторизация

`/join` доступен для захвата fragment до auth guard. Извлечь только валидный base64url token,
сразу `replaceState` очищает hash. Хранить pending token и createdAt в sessionStorage одной вкладки,
TTL 30 минут; fallback — память при отказе storage. Новая ссылка заменяет старую; preview expiry
может сократить срок. URL return только `/join`, секрет не включать в router search/query keys,
Query devtools data, analytics, логи или localStorage. Preview/accept вызывать непосредственно из
feature API без сохранения secret-bearing request/response в Query mutation cache; авторизацию
переиспользовать через общий Axios client. Результат создания ссылки держать в локальном состоянии.

Вход/регистрация и ссылки между ними переносят безопасный redirect, включая TOTP/recovery.
Успех авторизации очищает старую identity/query state, но сохраняет ещё действующее pending invite.
Явный logout/отмена/terminal 400/409/success очищают токен; expired-session переход сохраняет его
в пределах первоначального TTL. При success принять groupId, перечитать группу и открыть budget URL.
При 409 preview не содержит groupId: предложить `/groups`, не угадывать группу по имени.

Preview требует JWT, выполняется только по входу на join или явному retry, не по таймеру/focus.
Preview и accept расходуют общую квоту; при 429 уважать Retry-After для обоих. Валидационные и
terminal ошибки не раскрывают секрет. При потере ответа accept не повторять POST автоматически,
предложить проверить группы. Отсутствующий pending token объясняется предложением открыть ссылку.

### 9. Планы и долги переиспользуют UI с явными различиями

Планы: список с currency/status/includeArchived, форма без userId, close с accountId и фактическими
значениями без participantId. Показать planned и actual отдельно; API expenseId может вести в 404
после удаления, но план остаётся closed. Архив/read-only и права plan не равны правам нового расхода.

Долги: отдельная group create/update schema, server-owned remaining/status, principal изменяем только
до любой истории. Чтобы надёжно определить ограничение, использовать наличие repayment total, включая
cancelled, а server 409 остаётся окончательной проверкой. В деталях добавить историю и подтверждение
cancel; response `{debt,repayment}` применить к обеим сущностям. isIncome обязателен; при false
accountId отсутствует. Связанный income не исправляется обычным income API. Личные `/transactions`
и ручные remaining/status не заменяются групповыми `/repayments` и server-owned полями.

### 10. Проверка и оформление реализации

Адресные проверки нужны для риска изоляции, контрактов и денежных вычислений: scope/URL precedence,
late responses/identity changes, TTL/redirect, permissions, group DTO и ledger с несколькими страницами,
minor units, plan/debt origin/cancel. Не утверждать наличие рабочего общего `npm test`: подходящие
существующие node:test файлы запускать явной командой с необходимым TS/alias runtime и записать её.
Не добавлять runner или dependency только ради этого change; если запуск невозможен, описать предел.

Обязательные команды реализации: `npm run lint`, `npm run lint:architecture`, `npm run build`.
UI проверять через `npm run dev` на доступном dev API двумя пользователями: personal и две группы,
приглашение через регистрацию/TOTP, права, операции, saving/transfer, plan, debt repayment/cancel,
переключение во время запросов, архив, потеря членства, loading/empty/error и 320px/desktop.
Недоступный API не считать проверенным; для исполнения клиентских сценариев без upstream использовать
Postman simulation по существующему контракту. Одна проверка схем не заменяет браузерный сценарий.

## Risks / Trade-offs

- [Широкий охват существующих query call sites] → внедрять scope последовательно, проверить все
  widgets/features и запретить неявный fallback на personal в семейном экране.
- [Исторический ledger дороже snapshot endpoint и не имеет revision] → кэш/AbortSignal/инвалидация,
  проверка всех страниц, явный refresh при конкурентных изменениях; не выдавать неполную сумму за точную.
- [Секрет в sessionStorage доступен скриптам origin] → только tab-local TTL, очистка fragment/terminal,
  отсутствие постоянного хранения/telemetry/cache; это не способ защиты от XSS приложения.
- [Права могут устареть] → актуализация group DTO и 403 recovery, сервер остаётся authority.
- [Сеть после POST не гарантирует отсутствие записи] → retry=false, блокировка двойной отправки,
  проверка истории перед явным повтором; отсутствие idempotency не скрывается.
- [Архив блокирует исправление истории] → явное предупреждение до архива и read-only после него.

## Migration Plan

1. Реализовать change последовательно по tasks; личные URL/API остаются совместимыми.
2. Новый preference-key не требует переноса данных; старые не-scoped Query данные не persist-ятся
   и исчезают при перезагрузке/смене identity. Финансовые данные браузером не мигрируются.
3. Перед ручной проверкой подтвердить актуальную версию dev API и данные с явной валютой и owner.
   Не запускать seed/backfill/purge автоматически и не менять настоящие семейные данные.
4. После проверок сохранить результаты и UI screenshots без токенов в verification-артефакте change.
5. Откат фронта убирает групповое UI, но не удаляет группы/операции на сервере; namespaced preference
   может остаться неиспользуемым. Изменения бэка и его откат этим change не выполняются.

## Визуальная доработка управления бюджетами — 2026-10-20

По запросу пользователя семейные экраны оформлены в существующей монохромной системе проекта:
Card, Button, Input, Switch, QueryError, Skeleton, семантические цвета и Lucide-иконки.
Без новых зависимостей и изменений API/финансовых правил.

- Переключатель бюджета — компактная панель с текущим контекстом, настройками и управлением группами.
  Native select сохраняет клавиатуру, пагинацию и выбранную группу за пределами страницы.
- Список групп — адаптивные карточки с названием, типом, ролью и явным переходом в бюджет.
  Создание семьи имеет отдельную форму и короткое объяснение следующих шагов.
- Настройки — карточки сведений, собственного доступа, участников и приглашений.
  На desktop две колонки, на мобильном последовательное расположение без горизонтального скролла.
- Права участников представлены существующим Switch. Полное управление выдаётся прежним единым PATCH.
  Владелец имеет статичный блок полного доступа. Смена владельца и исключение остаются вторичными действиями.
- Удаление/выход отделены от ежедневных настроек. Все прежние подтверждения сохранены.
- Приглашения имеют явные состояния, отдельный блок готовой ссылки и подтверждение копирования.
  Секрет не отображается в разметке. Экран вступления использует тот же AuthShell и общие кнопки.
- Контекст бюджета в финансовых формах оформлен компактной нейтральной плашкой.
