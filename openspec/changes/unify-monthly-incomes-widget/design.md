# Design

## Context

Мотивация описана в `proposal.md`. Сейчас `widgets/incomes` создает `CardAmount` на каждую валюту,
но получает только одну общую страницу доходов и фильтрует ее на клиенте. Такая страница
не гарантирует полный или корректный краткий список для каждой валюты.
`CardAmount` содержит табличное раскрытие с источником, датой, суммой и подписью «всего:».

Счета уже используют общую оболочку, независимые действия строки и диалог с таблицами.
`AccountHistoryTable` показывает по 10 записей на клиенте; entity-запросы используют
`loadPaginatedHistory` и `sortHistory`, загружая все страницы и сортируя по дате и id.
Клиентский контракт доходов поддерживает `fromDate`, `toDate`, `currency`, `page`, `limit`,
но явного параметра сортировки в нем нет. Поддержка этих фильтров сервером здесь не проверялась.

Форма добавления пока не принимает валютный контекст. `AccountSelect` отображает несовместимые
и архивные счета отключенными; это не удовлетворяет требованию скрывать их.
Существующая спецификация разрешает накопительные счета: delta явно заменяет это поведение
для добавления из валютной строки. Исторические доходы этим фильтром не ограничиваются.

## Goals / Non-Goals

**Goals:** согласованное представление краткой и полной истории, отсутствие межвалютного
смешивания и пропусков страниц, сохранение стиля раскрытых доходов и FSD-границ.

**Non-Goals:** изменение контрактов backend, новый глобальный селектор валют, изменение годовых
виджетов, добавление редактирования/удаления доходов и изменение правил доходных погашений долгов.

## Decisions

### Общая оболочка и независимые действия

В `widgets/incomes` создать общую `Card.Base` и локальные компоненты строки валюты и диалога.
Валюты и полные итоги брать из существующего revenue-запроса, сохранять сортировку через
`sortCurrencyCodes` и резервную строку основной валюты при пустом ответе.
Загрузка пользователя и итогов дает структурный skeleton общей карточки без общей кнопки `+`.
Ошибка без данных остается внутри карточки; ошибка фонового обновления не скрывает пригодные данные.

В строке валюта/сумма — одно действие открытия деталей, рядом независимые `+` и стрелка.
Нельзя вкладывать кнопки друг в друга. Состояния раскрытий хранить по валюте; открытый диалог
хранить отдельно. При смене месяца диалог получает новый контекст и первую страницу, сохраняя
выбранную валюту; старые записи не подставляются под новый месяц. После закрытия фокус
возвращается к действию строки, а при исчезновении строки — к доступному элементу виджета.

Существующие классы и форматирование раскрытой таблицы перенести в локальную область строки
без переработки общего `CardAmount`, используемого другими карточками. Итог строки остается
виден наверху, под краткой таблицей сохраняются «всего:» и полный итог в прежнем оформлении.
Стрелка остается доступной и при пустой истории, чтобы показывать локальное пустое состояние.

### Процентное изменение относительно предыдущего месяца

Дополнительным revenue-запросом получить полный предыдущий календарный месяц, включая переход
январь → декабрь предыдущего года. Сопоставить итоги строго по валюте и использовать существующий
`getPercent(current, previous)`: `(current - previous) / previous`. При нулевом текущем доходе,
отсутствующей/нулевой базе и равных итогах результат скрыт. Запрос сравнения включать только
при наличии положительного текущего дохода; он не блокирует карточку. При ошибке без кэша diff
скрыт и доступен компактный повтор сравнения; пригодный кэш того же контекста сохраняется.
После кода валюты показать Body2, signed percent compact и стрелку size-4/strokeWidth 1.75
с прежними цветами text-success/text-destructive из CardAmount.

### Одна полная история на месяц и валюту

В `entities/incomes/api/incomes.query.ts` добавить опцию истории, ключ которой включает
месяц и валюту под существующим семейством списка доходов. Через `loadPaginatedHistory`
выполнить существующие запросы доходов с периодом и валютой до получения всех страниц;
использовать существующую сортировку по дате убыванию и id для равных дат с устранением дубликатов.
Не ограничивать историю `accountId` или типом счета.

Запускать историю только при раскрытии валюты или открытии ее диалога. Эти представления
используют один ключ и кэш: раскрытие берет первые 5 записей, диалог — страницы по 10.
Это повторяет подход счетов и гарантирует последние 5 даже без известной серверной сортировки.
Альтернатива — `limit=5` для раскрытия и серверная пагинация диалога — потребовала бы гарантии
сортировки backend, которой нет в текущем клиентском контракте. Лимит 5 здесь относится
к видимым операциям; в фоне краткое раскрытие может загрузить больше для правильного порядка.

Существующая инвалидация семейства доходов обновит эту историю и revenue после создания.
Не использовать данные другого периода как placeholder. Ошибки и skeleton истории локальны
строке или диалогу, обновление того же контекста сохраняет пригодные записи.

### Таблица и пагинация без связи между widgets

Перенести нейтральное представление `AccountHistoryTable` в shared UI с явными текстовыми
параметрами загрузки, ошибки, пустого состояния и пагинации. Счета подключить к нему с прежними
текстами и поведением; доходы — со своими i18next-ключами. В диалоге доходов скрыть видимый заголовок таблицы, сохраняя ее caption и доступное имя;
в деталях счетов секционные заголовки остаются видимыми. Общая таблица использует существующий
`paginateHistory`. Импортировать виджет счетов из виджета доходов нельзя.
Альтернатива с дублированием таблицы увеличивает риск расхождения доступности и пагинации.

Диалог доходов использует общий `Dialog`, ширину и паттерн возврата фокуса из деталей счета.
Колонки: дата, источник, счет, сумма. Названия счетов получить через существующий запрос счетов,
включая архивные; недоступное название заменить локализованной подписью, не блокируя историю.
Повторное открытие или изменение месяца/валюты сбрасывает страницу через контекст компонента.
Обновление с сокращением списка ограничивает страницу допустимым диапазоном.

### Валюта формы и допустимые счета

`CreateIncomeButton` получает обязательную валюту строки; сейчас его единственный потребитель —
месячный виджет. В feature отфильтровать загруженные счета по `archivedAt === null`,
`type === 'balance'`, совпадению валюты до передачи в общий `AccountSelect`, не меняя другие селекторы.
Предвыбор основного счета работает только по отфильтрованному списку; при отсутствии подходящего
основного выбор остается пустым. После обновления сбрасывать ставший недопустимым выбранный счет.

Проверять наличие выбранного допустимого счета и точность суммы непосредственно перед отправкой,
а не только через disabled кнопки. DTO остается прежним с `accountId`, без отдельной валюты.
При пустом списке сохранять существующий переход к созданию счета, уточнив текст про расчетный
счет нужной валюты. Создание обновляет список; неподходящий новый счет не появляется в селекторе.
Настройка формы создания счета и автоматический выбор любого первого счета не добавляются.

## Risks / Trade-offs

- [Полная история может быть большой] → загрузка только по действию пользователя, один кэш на
  валюту/месяц и существующие последовательные запросы по 100; серверную сортировку не вводить в этом scope.
- [Частичная история при ошибке одной страницы] → ошибка всей загрузки, без выдачи частичного списка
  за полный; повторить запрос, сохраняя ранее завершенный кэш того же контекста.
- [Вынос таблицы затронет счета] → сохранить их тексты, размеры страниц и действия; проверить детали
  счетов и обе независимые пагинации после переноса.
- [Фильтр счета изменится во время открытой формы] → повторная проверка допустимости на submit
  и сброс устаревшего выбора после обновления данных.
- [Нет общего работающего test runner] → документировать конкретные команды для затронутых
  `node:test` тестов; не считать bare `node --test` зеленой проверкой всего проекта.

## Migration Plan

Изменение только frontend, без миграции данных и новых зависимостей. Выпустить общей поставкой
после lint, Steiger, build и ручной проверки дашборда и деталей счетов. При откате вернуть
предыдущую frontend-версию; основной OpenSpec обновлять при штатном sync/archive после реализации.
